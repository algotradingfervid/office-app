# SHIPSHOW — turn your shitshow into a ship show

This repo runs the SHIPSHOW factory: a fixed set of stations that take a product
from idea to shipped features, one feature at a time, with agents doing the work
and a human deciding five times (spec, name, brand, wireframes, merge).

Run `/shipshow` at any time to see where the product is and what station is next.

## The stations (in order)

Floor 1, prove it (once per product):
`/brainstorm` → `/research` → `/spike` (when the risk is "can we do it") → `/define` (H) →
`/blueprint` → `/tool-up` → the line builds the **Core** tier

Floor 2, make it a product (runs while the line builds Core; before `/blueprint` when `design-timing: early`):
`/name-it` (H) → `/brand` (H) → `/design-system` → `/wireframe` (H) → the line builds **Usable**, then **Launch**

The line, once per story, in parallel waves:
`/slice` (one tier) → `/isolate` → `/build` → `/prove` → `/ship` (H) → `/learn` (once per wave)

(H) = the human decides. Everything else has a gate the agent checks itself.

## Where things live

- `factory/STATE.md` — the single source of truth for what is done and what is next, one screen long (≤ 60 lines). Read it first, update it last. History goes to `factory/HISTORY.md`, which you do not read unless asked.
- `factory/DIALS.md` — how much ceremony this product gets. Set at `/brainstorm`. Respect it.
- `factory/*.md` — spec, research brief, brand, architecture. Documents are the source of truth; code is temporal.
- `factory/stories/` — one file per story with status, prerequisites and expected files.
- `factory/evidence/` — before/after proof per story.
- `factory/lessons/` — what went wrong, feeding `/learn`.
- `.claude/skills/product-*` — the product kit, generated by `/tool-up`. Product-specific rules live there, not here.

## House rules (core, product-agnostic)

- One story per workspace, one agent per workspace. Never commit to `main` directly. A story agent never writes outside its own worktree (a hook enforces it).
- Start every story with a clean context. If you are carrying more than one story's worth of history, stop and start fresh.
- Tests or an acceptance check before code. Then the smallest change that passes.
- State assumptions out loud before acting on them. If the spec or wireframe is unclear, ask; do not guess silently.
- Touch only what the story needs. Do not refactor, "improve" or clean up neighbouring code unless the story says so.
- Prefer 100 lines over 1,000. No speculative abstractions, no defensive code for cases that cannot happen, no dead code left behind.
- Show evidence, not claims: the command you ran and its output, or the screenshot, or the recording.
- Design taste is the human's. Talk through the direction (brand, interface, layout) before drawing, not after.
- Look at visual work before showing it: render it with `scripts/look.py` and open the screenshots. A passing script is not a look.
- Review is done by a fresh agent, never by the one that wrote the code. Tag each finding BLOCKING or NOTE; only blocking findings are fixed before merge, in at most two rounds. 5/5 means "I would merge this myself."
- If a check fails twice for the same reason, write it to `factory/lessons/` before trying a third time.
- Guardrails are hooks, not requests. A station that must edit a protected file or commit to `main` writes its name to `.claude/station` first and removes it after. Never write that marker to bypass a guard for a story.
- Ask before anything irreversible: force-push, deleting data, dropping tables, spending money.

## Ceremony

Size the ceremony to the risk. Prove the core before building around it, and build one tier at a time.
`factory/DIALS.md` says which design rooms are on "quick" and when they run. On the line, each story's `lane` sets its ceremony:
`core` (one code reviewer, plus design if it has a screen) or `full` (every matching specialist reviewer; set by the product's risk paths). Throwaway measurements are `/spike`, not stories.
Stories are small (one outcome, ≤ 5 non-test files) and planned in waves that own disjoint files.

## Product: Office App (Go 1.27.1 + PocketBase v0.40.4, htmx, Pico.css)

Design (rules, data, security, ops): `docs/superpowers/specs/2026-09-25-office-app-leave-design.md`. Terms: `factory/GLOSSARY.md` (read it before naming anything).
Load `product-architecture` before writing or reviewing Go code; `product-proof` in /prove.

Commands
- `make check` — gofmt, vet, golangci-lint, import boundaries, all tests. The gate for everything.
- `go test ./internal/forms/leave/...` — one module's tests while building.
- `make run` — dev server on 127.0.0.1:8090 with demo data in ./pb_data (delete the folder to reset).
- `scripts/preview.sh` / `--stop` — this checkout on a free port with fresh demo data; prints the URL.
- `scripts/prove.sh <id>`, `scripts/mutate.sh <id>` — evidence and mutation (gremlins v0.6.0).
- Demo logins: E001 employee, E002 + E003 approvers, E004 HR admin; password `demo-pass-2026`.

Folders
- `cmd/officeapp` main · `internal/modules` the one module list · `internal/core/*` shared modules ·
  `internal/forms/*` one folder per form · `internal/testapp` test app · `docs/` design and HR policy.

Conventions
- A story's `files` claim is exact (test files `*_test.go` in the same folders are always allowed); a migration name given there wins.
- New migrations: `<module>/<unix-time>_<what>.go` with `m.Register(up, nil)`; unnamed ones take the current Unix time.
- New feature files register themselves: `func init() { addPart(func(app core.App) { ... }) }`.
- Tests use `testapp.New(t)` / `testapp.Factory` (never a hand-built app); code that needs "today" takes a `clock.Clock` (tests: `clock.Fixed`).
- Building a story from a session that is not in its worktree (e.g. a delegated agent): start every Bash
  command with `cd <abs worktree> &&`, use absolute paths inside it, and run `make check` yourself before stopping.
- Go needs no install step in a new worktree (shared module cache).

Gotchas
- Every read inside `RunInTransaction` uses `txApp`; the outer `app` deadlocks or reads stale data.
- Calendar dates are text `YYYY-MM-DD`; PocketBase `date` fields are UTC datetimes (off by one in IST).
- CSP forbids inline scripts/styles and `hx-on`; POST forms need `Sec-Fetch-Site` (tests: `testapp.FormHeaders`).

Risk paths (a story touching these is `lane: full`)
- `internal/core/auth/**` · `internal/core/approvals/**` · `internal/core/audit/**`
- `internal/forms/*/*ledger*`, `*balance*`, `*daycount*`, `*policy*`, `*form_hooks*`, `*jobs*` · anything serving attachments
- a migration that changes or drops an existing field/collection (new collections are fine) · `internal/core/web/web.go`
